# v1.0.2 发布阻断问题设计

## 目标

修复真实安装版验收中发现的两个发布阻断问题：助手快照请求在运行时尚未注册时可能丢失并于 60 秒后超时；旧藏扫描将跨收藏夹去重后的“主来源候选数”误当作收藏夹扫描结果，导致重复来源收藏夹数量偏小或完全消失。

## 助手运行时就绪协议

主窗口渲染进程注册 `assistant-runtime:request` 监听器后，必须主动向主进程发送 `assistant-runtime:ready`。主进程为每个主窗口跟踪就绪状态：页面开始重新加载或窗口销毁时清除，收到当前主窗口的 ready 信号时置为就绪。

所有助手运行时请求在发送前同时等待两个条件：Electron 页面加载完成、助手运行时明确 ready。等待仍受原有请求总超时约束。这样不通过加长超时掩盖问题，也不依赖 React `useEffect` 与 `did-finish-load` 的偶然顺序。

## 旧藏来源与计数口径

扫描结果保留 B站返回的全部收藏夹及其原始媒体数量，同时保留实际成功读取的有效视频数量。跨收藏夹按 `aid` 合并仅用于执行去重；每个唯一视频继续保存完整的 `sourceFolderIds` 和 `sourceFolderTitles`。

来源列表直接基于原始扫描收藏夹构建，不再从去重后的主来源预览反推。每个收藏夹即使本轮待整理数为 0 也必须显示。界面显示“共 N｜本轮待整理 M”：`N` 是 B站收藏夹报告的原始数量（缺失时退回有效读取数量），`M` 是未受保护的唯一视频中来源集合包含该收藏夹的数量。

勾选来源时按完整来源集合匹配。同一视频属于多个已选收藏夹时仍只生成一个执行项；原收藏夹关系不删除。全局扫描进度与总数继续按唯一视频计算。

## 错误与降级

- 单个收藏夹读取失败仍出现在来源列表，并标记为扫描失败，不伪装成 0 条。
- 失效或非视频媒体不进入执行候选；原始数量与有效数量不同的原因通过口径说明表达。
- 已整理保护视频不进入“本轮待整理”，但其来源收藏夹仍显示。
- 快照请求超时继续保留最终防线，但正常冷启动、刷新和快速切换不应依赖超时恢复。

## 测试

- 主进程单元测试覆盖：页面已加载但运行时未 ready 时不发送；ready 后发送；重载后重新等待；超时清理监听器。
- 收藏扫描/保护单元测试覆盖：同一视频属于多个收藏夹时只执行一次；两个来源都可筛选；全重复收藏夹仍出现在摘要中且待整理数可为 0；原始数量与候选数量分别保留。
- UI 测试覆盖来源文案和数量口径。
- 修复后重新执行完整测试、构建、dev、preview、Windows 打包、真实安装与干净配置验收。

## 范围外

不改变真实 B站收藏夹内容，不新增删除原收藏夹功能，不自动执行点赞、投币、收藏、评论或旧藏迁移。
