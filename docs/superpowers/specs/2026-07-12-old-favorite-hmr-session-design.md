# 旧藏整理开发态会话恢复设计

## 背景与根因

在 `npm run dev` 中执行旧藏 DeepSeek 整理时，Vite Fast Refresh/HMR 可能重新执行 `FavoriteLedgerPanel.tsx` 模块。现有 `oldFavoriteRuntimeSession` 是模块级 `Map`，模块被替换后会创建新的空 Map。与此同时，DeepSeek 后台任务和全局任务指示灯仍然继续，因此界面表现为：整理向导回到初始状态，但整理指示灯仍提示任务运行中。

助手标签和主浏览器标签的正常切换只会隐藏视图，不会卸载 `FavoriteLedgerPanel`。因此修复目标不是标签切换本身，而是让同一 renderer 会话中的状态在组件重挂载和 HMR 模块替换后仍指向同一个会话容器。

## 目标

- 开发版发生 HMR 后，正在运行的旧藏整理向导继续显示原预览、步骤、状态和进度。
- 异步 DeepSeek 任务在旧组件实例消失后，仍能把结果写入新组件订阅的同一会话。
- 真实归档执行重挂载后仍保持执行锁和进度，不能重复启动同一批操作。
- 恢复会话时保留草稿收藏夹和受保护视频重新整理进度，避免预览与实际执行配置脱节。
- 新扫描结果带有不同 B 站账户时丢弃旧会话，且旧异步任务不得回写新账户会话。
- 用户完成本轮并点击“好的”后清空会话，下一轮从干净状态开始。

## 非目标

- 不跨应用重启持久化正在运行的 DeepSeek 请求。
- 不在主窗口侧栏和独立悬浮助手两个 renderer 之间共享会话。
- 不把整个 DeepSeek 请求调度迁移到 Electron 主进程。
- 不改变现有旧藏整理步骤、推荐算法或 B 站执行脚本。
- 不在缺少当前账户身份接口时主动探测“页面已换号但尚未重新扫描”的情况；账户隔离以新扫描返回的 `accountMid` 为边界。

## 方案比较

### 方案一：`globalThis` 稳定会话单例（采用）

把 Store 挂到 `globalThis` 的全局 Symbol 上。HMR 会替换模块代码，但同一 renderer 的全局对象保持不变，新模块重新加载后取得原 Store。该方案改动集中、无需序列化，也允许旧异步闭包和新组件使用同一 Store。

### 方案二：`sessionStorage`

能够跨完整页面刷新保存可序列化状态，但复杂的 Set、预览快照和执行状态需要编码与迁移。完整刷新还会中断原 Promise 回调，容易留下“显示运行但没有任务接收结果”的假状态，因此不采用。

### 方案三：Electron 主进程任务管理器

可以跨 renderer 和窗口恢复，是最完整的长期架构，但需要新增 IPC 任务协议、结果缓存与取消语义。当前问题只发生在开发态 HMR，投入与风险过大，因此不采用。

## 架构

新增一个独立的旧藏会话 Store 模块，负责：

- 通过 `Symbol.for` 或等价的稳定全局键从 `globalThis` 读取或创建 Store。
- 保存键值状态、订阅者集合和当前账户标识。
- 提供读取、更新、订阅、重置和账户校验接口。
- 测试环境可显式重置，但生产代码不因普通组件卸载而重置。

`FavoriteLedgerPanel` 继续通过 `useSyncExternalStore` 订阅状态，但不再自行拥有模块级 Map。旧异步任务捕获的 setter 与 HMR 后新组件取得的 setter 都操作全局 Store。

## 会话状态范围

会话至少保存以下状态：

- 当前预览与基础扫描预览。
- 当前步骤和整理模式。
- 来源收藏夹、候选收藏夹选择和归档计划。
- 草稿收藏夹 `draftLedgers`。
- 已重新整理的受保护视频 aid 集合。
- DeepSeek 模式、运行状态、取消请求、文字状态、进度、建议数量和运行快照。
- 预览提示、撤销栈、重做栈和最近改动。
- 真实归档执行状态、执行进度和等待用户确认状态。
- 向全局状态灯回放的旧藏状态快照。

纯瞬时 UI 状态，例如拖拽目标、弹层开关和滚动焦点，仍保留在组件本地；重挂载后关闭这些瞬时界面是可接受行为。

## 账户隔离

扫描结果中的 `scanContext.accountMid` 是会话账户标识。Store 在首次得到有效账户时绑定该账户。后续扫描发现不同的有效账户时，先清空旧会话再接受新数据。

如果尚未扫描出账户标识，Store 可以继续保存准备阶段状态；但不得把带账户的旧预览用于另一个已识别账户。

当前组件没有独立的“读取当前登录账户”接口，因此仅在用户重新扫描后才能识别外部换号。若未来 IPC 提供轻量账户身份查询，应在恢复预览和真实执行前增加校验。

## 异步任务与副作用

DeepSeek 结果首先写入 Store，界面和状态灯从 Store 派生显示。必须避免依赖已卸载组件的本地执行锁。

需要保留的外部副作用包括关键词建议持久化和阶段反馈。它们必须具备幂等性：同一个 DeepSeek 运行结果只能提交一次。Store 为运行保存唯一 run id 和完成标记，新组件可以接管尚未交付的完成副作用，旧组件即使继续回调也不能重复提交。

取消操作只标记当前 run id；新运行创建新 id，旧运行的取消标记不能污染下一次运行。

## 真实归档执行

真实执行开始前在 Store 中原子地把状态从 `idle` 改为 `running`。所有入口都依据 Store 锁判断，组件重挂载后仍无法重复启动。

执行进度逐条写入 Store。完成后进入 `awaiting-acknowledgement`，保持最终结果和进度，直到用户点击“好的”。用户确认后统一清理预览、草稿、执行状态和 DeepSeek 状态。

## 错误处理

- DeepSeek 失败时把 Store 状态从 `running` 更新为 `error`，不得让全局状态灯永久停留在运行中。
- HMR 后若 Store 表示运行中，但不存在可继续回写的 run 句柄，则显示明确的“开发热更新中断了请求，请重新开始”状态，不伪装为仍可完成。
- 账户变化时清空旧会话并提示需要重新扫描。
- Store 更新采用函数式更新，避免旧闭包覆盖新组件刚写入的状态。

## 测试设计

### Store 单元测试

- 设置会话状态后重新加载 Store 模块，验证 `globalThis` 上的同一 Store 被复用。
- 重置 Store 后所有字段回到初始值。
- 不同账户绑定时旧预览被清理。
- 取消标记只作用于对应 run id。

### 组件集成测试

- DeepSeek 请求未完成时卸载并重挂载面板，预览、步骤和进度仍显示；请求完成后新面板显示结果。
- 真实归档执行期间重挂载，确认按钮保持锁定，不能第二次调用执行函数。
- 重挂载后草稿收藏夹与受保护视频进度保持一致。
- DeepSeek 失败后状态灯不再显示运行中。
- 完成并点击“好的”后，会话被清空。

### 回归验证

- 运行 `FavoriteLedgerPanel` 与 `FloatingAssistantApp` 相关测试。
- 运行完整 Vitest 测试集；若仓库存在与本次无关的既有失败，单独记录。
- 运行构建命令，确认生产构建不依赖 Vite HMR API。

## 成功标准

在 `npm run dev` 中触发旧藏 DeepSeek 整理并发生组件重挂载或模块热替换后，固定侧栏仍展示同一整理会话；后台状态灯与向导状态一致；真实执行不会重复启动；用户结束本轮后会话可正常清空。
