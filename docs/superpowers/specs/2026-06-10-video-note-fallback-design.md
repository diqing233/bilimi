# Bilimi 视频札记总结兜底设计

- 日期：2026-06-10
- 状态：已确认的补充设计草案
- 主题：未能识别视频文档时，继续进行札记总结

## 1. 背景

Bilimi 现有第一阶段设计要求将当前推荐项或当前视频呈现为一条奏折条目，并提供摘要、批语与动作签条。后续“札记”能力需要从视频相关材料中生成笔记总结。

新的补充场景是：当系统未能识别到结构化的视频文档时，不能把用户停在失败状态，而应进入札记总结兜底流程。用户确认采用混合兜底：先自动抓取当前页面可用材料；如果材料不足，再请求用户手动补充字幕、文稿、简介或零散记录。

## 2. 目标

1. 视频文档识别失败后，仍然允许用户完成札记总结。
2. 自动优先收集页面上可见或可读取的视频材料，尽量减少打断。
3. 材料不足时，清楚提示用户补充内容，而不是编造总结。
4. 生成的札记结构稳定，可被后续收藏、复看和偏好记录使用。
5. 文案保持 Bilimi 的奏折风格，同时让失败原因和下一步动作易懂。

## 3. 不做的内容

1. 不在当前补充设计中引入完整的视频语音转文字能力。
2. 不保证每个 Bilibili 页面都能读取字幕或 AI 字幕。
3. 不在材料不足时生成看似完整但缺乏依据的总结。
4. 不把用户粘贴的补充材料自动发往平台评论区或其他外部位置。
5. 不改变原有“赏 / 赐 / 表 / 阅”主链路定义。

## 4. 用户体验

当用户触发札记总结，但视频文档识别失败时，界面进入“拟札”状态。

若自动收集到足够材料，助手直接生成札记，并显示来源提示：

> 未识得视频文档，臣先据页面材料拟札。

若自动材料不足，助手显示补充输入区，并给出清楚的下一步：

> 未识得视频文档，现有材料不足成札。若陛下赐下字幕、文稿或观后零札，臣可再拟一版。

补充输入区支持用户粘贴：

1. 视频字幕或 AI 字幕。
2. 视频文稿、简介、评论区摘要或其他文本资料。
3. 用户自己的零散笔记。

用户补充后，可重新生成札记。重新生成后的札记需要标注“据补充材料拟札”，避免让用户误以为全部来自自动识别。

## 5. 数据流

### 5.1 识别入口

`VideoDocumentDetector` 尝试识别结构化视频文档，返回三类结果：

1. `found`：已识别到可总结的视频文档。
2. `low_confidence`：识别到部分材料，但可信度不足。
3. `not_found`：未识别到可用视频文档。

`low_confidence` 和 `not_found` 都进入札记总结兜底流程。

### 5.2 自动材料收集

`NoteSourceCollector` 从当前页面上下文收集可用材料：

1. 视频标题。
2. UP 主名称。
3. 视频简介。
4. 分P标题与章节信息。
5. 标签、分区和发布时间等页面元信息。
6. 可读取的字幕或 AI 字幕文本。
7. 当前页面 URL。

收集结果统一整理为 `NoteSourceBundle`，并保留每段材料的来源类型。

### 5.3 材料质量判断

`SourceQualityScorer` 判断材料是否足够生成札记：

1. 若有字幕、AI 字幕、文稿或较完整简介，则判为 `sufficient`。
2. 若只有标题、UP 主、标签和 URL，则判为 `insufficient`。
3. 若有少量简介但缺少主体内容，则判为 `partial`。

`sufficient` 可直接总结。`partial` 可生成轻量札记，但必须提示“材料有限”。`insufficient` 必须请求用户补充。

### 5.4 手动补充

当材料不足时，`ManualSourcePrompt` 展示输入区。用户提交后，补充文本与自动收集材料合并为新的 `NoteSourceBundle`，再次交给 `SourceQualityScorer` 判断。

补充内容不覆盖自动材料，而是作为 `manualSupplement` 附加保存，便于札记展示来源。

## 6. 札记输出结构

`NoteSummarizer` 输出稳定结构：

1. 一句话概要：用一句话说明视频核心内容。
2. 关键要点：列出 3 到 5 条主要信息。
3. 值得复看处：指出最值得回看或深挖的部分。
4. 疑问 / 待查：列出材料中无法确认或值得继续查证的点。
5. 标签：生成 3 到 6 个便于归档的标签。
6. 来源提示：标注“据视频文档”“据页面材料”“据补充材料”或“材料有限”。

材料不足时，札记必须避免确定性过强的表达。例如不能把标题推测成视频结论，也不能把标签推测成完整主题。

## 7. 错误处理

1. 页面材料读取失败：显示“未能取全页面材料”，允许用户手动粘贴。
2. 字幕读取失败：不阻断流程，继续使用标题、简介等其他材料。
3. 用户提交空补充：保持补充输入区，并提示需要有效文本。
4. 总结生成失败：保留已收集材料和用户补充，允许重试。
5. 材料质量仍不足：不生成完整札记，只生成“待补材料”草稿。

## 8. 模块边界

### `VideoDocumentDetector`

负责判断是否存在结构化视频文档。它只返回识别结果和置信度，不负责总结。

### `NoteSourceCollector`

负责从页面和当前视频上下文中收集材料。它不判断材料是否足够，也不改写内容。

### `SourceQualityScorer`

负责将材料评估为 `sufficient`、`partial` 或 `insufficient`，并给出原因。

### `ManualSourcePrompt`

负责展示补充输入区、接收用户文本，并把补充材料交回总结流程。

### `NoteSummarizer`

负责根据材料生成札记。它必须接收来源信息，并把来源提示写入输出结果。

## 9. 测试策略

单元测试覆盖：

1. `VideoDocumentDetector` 返回 `not_found` 时进入兜底流程。
2. 自动材料含字幕时，`SourceQualityScorer` 返回 `sufficient`。
3. 自动材料只有标题和 URL 时，`SourceQualityScorer` 返回 `insufficient`。
4. 用户补充有效文本后，可重新进入总结。
5. 材料有限时，输出中包含来源提示和限制提示。

集成测试覆盖：

1. 识别失败后，界面显示“据页面材料拟札”或补充输入区。
2. 自动材料不足时，不直接生成完整札记。
3. 用户粘贴补充材料并提交后，界面展示札记总结。

人工验证覆盖：

1. 有字幕的视频页面。
2. 无字幕但有完整简介的视频页面。
3. 只有标题和少量页面信息的视频页面。
4. 页面结构变化导致自动读取失败的情况。

## 10. 成功标准

1. 用户在视频文档识别失败后，不会只看到失败状态。
2. 自动材料足够时，用户无需额外输入即可得到札记总结。
3. 自动材料不足时，用户能明确知道需要补充什么。
4. 生成的札记不会伪装成来自不存在的视频文档。
5. 后续实现计划可以基于本设计拆分为检测、收集、评分、补充输入和总结五个清晰模块。
