## 讨论诊断结论（只读）

1. “已保护跳过”读取的是收藏仓库的 `organizationRecords`，不是转写模型目录，也不是单独的标签缓存。增量扫描会把已有 `organizationRecords` 的视频排除，避免再次分类。
2. 截图中选中的 `bilimi·影视动漫` 显示 `0 个视频`，只能证明该文件夹当前没有可见项目；左侧“默认收藏夹 257”仍说明该收藏库并非完全没有数据。
3. 本机开发档案中当前账号仍存在 257 条收藏视频和 132 条已完成整理记录；后者会让下一次增量扫描显示“已保护跳过”。这解释了“清空后仍跳过”的数据条件，但尚未证明用户当时点击的是哪一种清空操作。
4. “从收藏库 bilimi 收藏夹删除”按现有产品语义只移除本地工作夹归属，明确保留保护及处理记录；之后增量扫描仍跳过，这是现有设计的结果。若用户的“清空收藏库”指此操作，则行为与用户预期冲突，需要另行决定清空时是否同时撤销保护。
5. 正式安装版的卸载器只有在勾选“同时删除 bilimi 用户数据”时才删除 `%APPDATA%\\bilimi`，其中包含收藏仓库；未勾选会保留。`npm run dev` 使用 `%APPDATA%\\bilimi-dev`，安装包卸载器不会删除该开发档案。完整“清除全部用户数据”功能也会删除其当前运行档案下的收藏仓库。

## R002 补充后的根因修正

卸载勾选“同时删除 bilimi 用户数据”只会删除本机档案，不会删除 B 站服务器上的收藏夹及其成员关系。重新登录后，扫描会发现仍留在 B 站的已绑定 `bilimi·…` 工作夹；当这些工作夹被确认绑定时，扫描会把其中成员重新写为本地 `initializedRecords`，再计入 `protectedAidSet`。因此本地收藏库在卸载后初始为空、扫描却出现“已保护跳过”，在当前设计下是可复现的远端恢复行为，而非必须存在卸载漏删。

截图中的“已发现 11 个 B站收藏夹；已扫描 255 条已保护视频”正是该远端恢复路径的界面证据。另行发现当前正在运行的实例是开发版，使用 `%APPDATA%\\bilimi-dev`；安装包卸载不会删除此目录，故测试时应避免把开发档案残留和安装版清理结果混为一谈。
