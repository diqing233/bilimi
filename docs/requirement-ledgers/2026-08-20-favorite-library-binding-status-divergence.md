## 只读排查记录

- 运行中的 Electron 开发版明确使用 `C:\Users\diqing\AppData\Roaming\bilimi-dev`，不是默认 `bilimi` 数据目录；此前默认目录与截图不一致的疑点已排除。
- 截图对应账户的收藏库仓库快照（revision `7859`）中，8 个 `bilimi-logical:*` 工作夹均仍为 `syncState: 'bound'`，但 `physicalShards` 为 `[]`。因此左侧 `favoriteLibraryLedgerBindingStatus()` 只读 logical folder 的 `bound`，会显示`已备册`；它没有再校验是否存在任何正式物理分册。
- 该快照的上一代（revision `7858`）尚有 1 条音乐分册；revision `7859` 新增命令 `favorite-release-default-binding:*`，其类型为 `remove-physical-shard-binding`。当前命令实现移除了 physical shard、physical folder 与成员映射，却没有重新计算受影响 logical folder 的 `syncState`；故最后一条分册移除后仍留下逻辑`bound`标记。其余 7 个无 physical shard 但 logical 为`bound`的历史来源已超过当前两代持久化保留窗口，不能凭空归因；不过都违反同一个应有不变量。
- 截图时右侧规则数据是`bindingState: 'unbound'`并保留`managedFolderDeletedByUser: true`及历史远端 ID；这正表示用户曾明确解除默认工作夹的本地绑定，不能被旧数据静默恢复。
- 之后的只读排查期间，运行中应用自行写入了新的偏好快照：同一批规则变为`bindingState: 'bound'`，但`managedFolderDeletedByUser: true`仍存在，仓库仍无 physical shard。未由本轮命令写入应用数据。代码链路与这个结果精确吻合：`favoriteLedgerApi.ts` 的`syncLedgerFolderIds()`一旦发现规则保留的远端 ID仍在 B 站清单，就无条件回写`bindingState: 'bound'`，没有识别该用户解除标记；`App.tsx`的`readFavoriteLedgerStatus()`随后把核验结果保存回 preferences。
- `App.tsx`的`projectFavoriteLedgersToFormalBindings()`本来只在`managedFolderDeletedByUser && bindingState === 'unbound'`时拒绝旧仓库投影；状态脚本已经把`unbound`反写成`bound`后，这一层保护失效。故问题不是刷新慢，而是“删除意志保护”的判断条件过窄，加上 logical folder 状态未从 physical shard 派生。

### 当前已证实的状态转换缺口

| 情况 | 当前实际行为 | 与截图/既有设计的冲突 |
|---|---|---|
| 默认工作夹解除本地绑定 | 右侧先显示`未绑定`，远端 ID 和`managedFolderDeletedByUser`仍保留 | 合理，表示尚未由用户显式重新备册。 |
| 最后一个 formal physical shard 被解除 | 逻辑工作夹仍保留`syncState: 'bound'` | 左侧错误显示`已备册`，与右侧`未绑定`分裂。 |
| 随后的普通 B 站状态核验 | 仅凭保留远端 ID 把右侧规则重新写成`已绑定` | 未经用户“备册 / 确认绑定”授权，反向撤销用户解除意志。 |

### 讨论中的最小修复方案（尚未实施）

1. 让 logical work folder 的状态严格由其 physical shards 推导：只有至少一个 shard 且全部为正式`bound`、各自有远端 ID时才是`bound`；零 shard 或任一未确认 shard均为`pending-reconcile`。`remove-physical-shard-binding`和所有未来绑定变更都必须重新计算受影响 logical ledger。
2. 为已落盘的“logical=bound、physicalShards=0”旧状态增加一次仅本地的确定性修复：只修正仓库状态和 UI 投影，不读取、不创建、不删除、不改名 B 站收藏夹，也不移动视频。该修复要在触发收藏库展示前完成，避免用户再看到旧标签。
3. 只要`managedFolderDeletedByUser`仍存在，状态核验和 repository 投影都必须把该默认规则视为`未绑定`；历史 remote ID只能作为之后用户点击备册、在确认页显式选择时的候选证据，不能自行恢复正式绑定。正式确认绑定成功后已有主进程回调负责清除该标记。
4. 状态矩阵保持既有删除边界：默认规则仍在但用户解除绑定 → 两侧`未绑定`；规则真实删除并保留恢复窗口 → 左侧`收藏夹已删除`和`恢复当前收藏夹`；远端工作夹确认删除而规则仍在 →`未备册`；至少一个正式分册存在 →`已备册`。不以名称猜测或自动认领同名 B 站夹。
5. 实施时须补共享仓库、状态核验脚本、App 投影和收藏库界面的回归用例，并在真实 Electron 中验证：解除后不反弹、重启后仍一致、显式确认绑定后才同时恢复`已备册`，以及零视频工作夹仍可正常显示。
