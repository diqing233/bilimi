## 讨论证据

- 批次下拉框通过 `onSelectSegment` 调用 `useOldFavoriteWorkspace.selectSegment`；该调用只发送 `select-segment` 命令。
- `OldFavoriteWorkspaceCoordinator.selectSegment` 会先持久化当前批次选择，再调用 `restoreFromStore` 重新加载工作区。该加载路径同时用于应用/工作区恢复。
- `restoreFromStore` 发现全局标签补取状态为 `running` 且仍有 `pendingAids` 时，会持久化写入 `status: 'paused'`。这是恢复安全保护，避免恢复后后台标签请求在没有明确继续操作时自行运行；当前实现也会在批次切换时进入这条恢复路径。
- “标签补取已暂停”读取的是全局 `tagEnrichment.status`；但截图处于“当前批次”视图，`已处理 2000 / 2000` 读取的是当前批次的 scoped tag counts。因此这两个数值口径不同：当前第 1 批可以已完成，而第 2 批仍有待补取项且整个队列已被暂停。
- 这不会把基本信息扫描改成暂停：截图中的扫描进度已经完成。它会停止后续未完成批次的标签抓取，直到用户点击“继续补取标签”。
- 若全局确实没有任何待补取项，状态理应为 `complete`；仅凭当前批次的 `2000 / 2000` 不能证明全局队列为空。

## 已确认的实施方向

- `R002`：将“批次切换”从恢复安全保护中排除。切换仅加载/选择批次，不暂停全局标签补取队列。

## 实施与验收记录

- 根因：`selectSegment` 调用 `restoreFromStore`，后者将 `running` 且仍有待补取项的标签队列持久化为 `paused`；该机制原本只服务于真实恢复后的安全保护。
- 实现：为私有恢复方法增加 `pauseRunningTagEnrichment` 策略；仅批次切换传入 `false`，应用/工作区真正恢复的调用保持默认值，因此仍会安全暂停。
- 失败回归证据：新增 501 个未带标签视频、分为两批；旧实现切换至 `segment-2` 后，断言收到 `status: 'paused'`（命令 exit 1，符合预期红灯）。
- 通过证据：定向新增测试 exit 0；新增测试与“重启后仍暂停”既有测试共同运行 2/2 通过；`npm test -- electron/main/oldFavoriteWorkspaceCoordinator.test.ts` 为 280/280 通过；`npm run build` exit 0。
- 界面验收：已尝试只读连接真实 Electron 窗口，但当前 Windows 自动化运行时未暴露其文档所述控制接口，因而没有执行鼠标切换、没有修改用户/B站数据。截图中“批次下拉切换后仍显示标签补取运行”的视觉状态待在开发版手动核验。
