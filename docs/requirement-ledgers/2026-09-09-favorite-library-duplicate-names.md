## 调查结论与证据（非用户原文）

1. 截图中的上下两组不是同一个列表被意外排序，而是两种不同身份的记录：

   - 上方“bilimi 工作夹”是 `bilimi-logical:<ledgerId>`，代表 bilimi 的本地逻辑分类及其本地成员归属，例如 `bilimi-logical:game` 有 42 个成员、`bilimi-logical:creative-aesthetic` 有 25 个成员。
   - 下方“其他收藏夹”是 `bilibili:<remoteFolderId>`，代表 B站原始收藏夹镜像，例如 `bilibili:4011793111` 的标题也是 `bilimi·游戏专区`，但它是独立的远端 ID。

2. 代码在 `src/renderer/src/features/favorites/FavoriteLibraryApp.tsx` 中明确按来源分组：`source === 'bilimi-logical'` 或带逻辑 ID 的本地草稿进入 `bilimi 工作夹`；其余非暂存记录进入 `其他收藏夹`。因此只要归并前提不成立，同名远端夹就必然落到下面。

3. 代码在 `electron/main/favoriteRepositoryService.ts` 中只会在存在唯一、可核验的 `physicalShards` 远端绑定时，把物理 B站夹 canonicalize 到逻辑工作夹。当前账号生产快照 `C:/Users/diqing/AppData/Roaming/bilimi/favorites/repository-v1/accounts/3706984597555811` 的 revision `308` 中，8 个默认逻辑夹的状态为 `pending-reconcile`，`physicalShards` 为空；这意味着系统当前没有足够证据证明这些远端 ID 分别对应哪个逻辑工作夹。

4. 同一快照仍保留同名远端镜像及其独立 ID：

   - `bilibili:4011793111` → `bilimi·游戏专区`，镜像成员数 0；
   - `bilibili:4017817711` → `bilimi·影视动漫`，镜像成员数 1；
   - `bilibili:4071794311` → `bilimi·创意美学`，镜像成员数 0；
   - `bilibili:4032813811` → `bilimi·搞笑杂谈`，镜像成员数 0；
   - `bilibili:4077791211` → `bilimi·生活日常`，镜像成员数 0；
   - `bilibili:4014797011` → `bilimi·音乐舞台`，镜像成员数 0；
   - `bilibili:4029818111` → `bilimi·暂存`，镜像成员数 0；
   - `bilibili:4041757711` → `bilimi·知识学习`，镜像成员数 0。

5. 所以“同名”只能说明标题相同，不能说明是同一个收藏夹；“分到下面”是当前安全策略的结果：绑定证据丢失或处于待对账时，远端实体不自动冒充逻辑工作夹。下面的 0 也不是上方本地分类数量被清空，而是该远端镜像当前记录的远端成员数。

6. 本轮没有修改业务代码、没有触发B站写操作，也没有改变账号数据。若要消除视觉上的重复，下一步需要用户明确“开始”后再讨论并实施展示/绑定收敛方案；不能仅按同名自动合并，因为这会有把不同远端收藏夹错误绑定到同一逻辑分类的风险。

### R009 核查结论（非用户原文）

1. 这里不是批量并发造成的竞态。`FavoriteRepositorySyncService.deleteManagedRemoteFoldersWithBridge` 对候选逐个 `await bridge.deleteFolder(...)`；不会同时发送多个删除请求。
2. “生活日常”已经通过回执或目录核对确认删除；处理到“搞笑杂谈”时，B站删除结果未能可靠确认。代码随后只会做一次按精确 `folder ID` 的目录核对；核对仍不能确认时便返回，后续“暂存”等候选绝不会执行。
3. 单个删除之所以看起来正常，是因为它只需跨过自己的一个请求和一次核对，不会被批次中另一个收藏夹的未知结果截停。它并不证明批量的实际删除请求写法不同。
4. 这是安全策略与可诊断性不足的组合：停止是正确的，避免对“可能已删”的目标盲目重发；但当前没有将该次未知结果的结构化诊断持久化，也没有为剩余“未执行”项提供安全的继续入口，因此用户体验上表现为“批量删除会 bug”。

### R011 核查结论（非用户原文）

1. 该规律对应一个已证实的批量删除实现缺口：`deleteManagedRemoteFoldersWithBridge` 在成功删除后直接进入下一次 `folder/del`，没有任何间隔、退避或事件循环让步。
2. 同一个 `FavoriteRepositorySyncService` 的普通同步批处理却在每次已完成远端操作之间调用 `sleep`，默认随机等待 1,200–2,000 毫秒。这说明项目本身已经承认连续 B站写需要节流，但收藏夹远端删除遗漏复用了该保护。
3. 因此“单个操作稳定成功、批量连续操作在第 2/3 项附近失败”与该缺口高度一致；名称候选不会造成按数量阈值稳定失败。
4. 目前无法仅由持久化数据把 B站的具体拦截类型断定为限流：删除路径未保存失败时的 HTTP 状态、B站 code、内容类型和请求时间线。实施前后应补齐这份可审计诊断，并只对可证明未写入的拒绝做退避重试；结果未知仍须先按精确 ID 对账。
