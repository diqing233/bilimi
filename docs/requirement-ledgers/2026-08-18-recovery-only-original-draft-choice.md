## 本轮讨论结论记录

- 当前代码不是渲染器固定只画一个按钮；渲染器按主进程返回的 `recoveryChoices` 动态显示按钮。
- 主进程仅在基线事实发生变化时加入“合并最新变化”；仅在状态为 `scanning` 或 `previewing` 且没有冻结同步计划时加入“重新扫描”；仅在状态为 `previewing` 且没有冻结同步计划时加入“放弃本轮整理”。
- 因此，若当前草稿已经进入冻结/执行相关状态，且基线没有变化，安全选项可能确实只剩“按原草稿继续”。具体状态仍需以运行中的主进程权威快照确认，不能只凭截图猜测。
- 项目书当前规定已有未完成草稿按当前事实与当前规则恢复并保留人工分类，但没有把恢复弹窗各选项在“冻结同步计划/执行中/已保存本地结果”等状态下的完整显示矩阵写全；这是本轮需要用户确认的产品设计缺口。

## 实施回读与验收记录（2026-08-18）

实施前已重新通读 R001-R004 原文和本表索引。按讨论顺序确认的范围如下：

1. `R001`：核查“只剩原草稿继续”的原因，并将普通草稿的用户操作从状态投影中统一为产品确定的恢复模型。
2. `R002`：恢复入口展示前，扫描/标签、DeepSeek、确认执行意图和 B 站同步均先安全暂停并持久化检查点。
3. `R003`：以历史提交和测试还原旧入口，旧按钮仅作为历史对照，不再作为当前用户操作。
4. `R004`：普通草稿固定显示`恢复草稿`、`重新扫描`、`放弃本轮整理`；无草稿直达扫描；`恢复草稿`内部采用 `merge-latest`，不再让用户选择内部决策。

明确保留但不作为普通草稿按钮的条目：`result-unknown` 的检查同步结果、工作镜像损坏的重建入口，以及持久化兼容所需的 `continue-original`/`merge-latest` 内部决策值。没有用户明确要求删除这些专属恢复或存量迁移能力，因此未从主进程协议和历史测试中删除。
